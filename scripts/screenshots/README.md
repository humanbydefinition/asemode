# Screenshot Scripts

This directory contains scripts that automate capturing, validating, and publishing screenshots of all Asemode panels, dialogs, transient loading states, warning variants, and modal alerts in both light and dark themes.

Screenshots generated by these scripts are published to `docs/images/screenshots/` and cataloged in [`docs/SCREENSHOTS.md`](../../docs/SCREENSHOTS.md).

## Prerequisites

Automated screenshot generation requires:

- **Operating System**: macOS (`darwin`) with an active, unlocked graphical desktop session.
- **Aseprite**: Version 1.3.18.6 or later.
- **Environment Variable**: Set `ASEPRITE_PATH` if Aseprite is installed in a non-standard location.

> [!IMPORTANT]
> The capture pipeline cannot run in headless continuous integration environments. It requires an active display server to render and capture native Aseprite UI dialogs.

## Directory Overview

| File / Directory | Purpose |
| :--- | :--- |
| `catalog.json` | Single source of truth defining supported themes, gallery categories, Lua suites, and all 60 screenshot targets. Read natively by both Node.js and Lua. |
| `manifest.mjs` | Loads `catalog.json`, exports catalog metadata, and parses/validates CLI filter flags (`--suite`, `--only`, `--theme`). |
| `generate.mjs` | Main Node.js orchestrator. Sets up isolated Aseprite profiles, pre-authorizes all `.lua` scripts, runs captures, and triggers publication. |
| `publish.mjs` | Validates captured PNG files (including duplicate detection within each theme), updates `docs/images/screenshots/`, and renders the categorized gallery in `docs/SCREENSHOTS.md`. |
| `capture.lua` | Concise Lua entrypoint executed inside Aseprite. Initializes the harness and fixtures, runs the requested suites, and verifies catalog completeness. |
| `lib/harness.lua` | Host automation engine. Intercepts `Dialog`, `Timer`, `Task.new`, and `app.alert`, tracks open windows on a stack, and exposes the title-agnostic `DialogHandle` API. |
| `lib/fixtures.lua` | Generates temporary TTF/JSON fixtures and resets the sample textmode sprite/layer state before each suite. |
| `suites/*.lua` | Six modular domain story suites (`panel.lua`, `about_settings.lua`, `document_grid.lua`, `fonts.lua`, `portable.lua`, `alerts.lua`). |

## How It Works

```text
catalog.json -> generate.mjs -> Isolated profile -> capture.lua
catalog.json -------------------------------------> capture.lua
capture.lua -> Harness and fixtures -> Suites -> publish.mjs -> Gallery
```

The profile authorizes scripts using SHA-1 hashes. The publisher validates PNG headers, dimensions, and uniqueness before it updates the screenshot images and gallery.

### 1. Declarative Catalog & Live Title Introspection (`catalog.json`)

All screenshot definitions live in `catalog.json`, organized into 6 categories (`panel`, `about-settings`, `document-grid`, `fonts`, `portable`, `alerts`).

- **Zero Duplicated Header Labels**: `catalog.json` never hardcodes dialog titles, tab labels, or loading task headers. Instead, `lib/harness.lua` introspects the live `Dialog` title, active `:tab()` label, `TaskRunner` progress title, or `app.alert` header directly from `src/ui/` at capture time and writes the resolved titles to `titles.json` for `publish.mjs`.
- **Optional State Variants**: When multiple screenshots capture different states of the same dialog (e.g., locked layer warnings or validation errors), `catalog.json` specifies only a short `"variant"` state descriptor, which `lib/harness.lua` combines with the live dialog header from `src/ui/`.

### 2. Title-Agnostic `DialogHandle` Automation (`lib/harness.lua`)

Instead of coupling scenarios to window header strings or button labels:

- `harness:open(fn, opts)` intercepts the newly opened dialog on top of the window stack, applies optional `{ tab = "..." }` or `{ loading = ... }` options, and returns a fluent `DialogHandle`.
- `dlg:set(field, value)` automatically updates file pickers, comboboxes, checkboxes, or text entries and invokes any registered `onchange` handler.
- `dlg:click(buttonId, opts)` and `dlg:clickAndOpen(buttonId, opts)` match buttons strictly by their semantic widget `id` in `src/ui/`, pause `TaskRunner` progress dialogs when `{ loading = ... }` is specified, and verify modal alerts when `{ alert = ... }` is specified.

### 3. Validation and Atomic Publication (`publish.mjs`)

Before updating repository assets on a full run, `publish.mjs` verifies the integrity of the captured image set:

- **PNG, Uniqueness & Title Validation**: Confirms valid PNG file signatures (`0x89504E47`), proper `IHDR` chunks, positive width and height metrics, distinct SHA-256 contents within each theme, and consistent runtime-introspected `src/ui/` titles across themes.
- **Atomic Deployment**: Stages changes in a temporary directory within `docs/images/`, swaps in the validated image set, and renders `docs/SCREENSHOTS.md` with a Table of Contents and categorized sections.

## Usage

Run the full screenshot generator from the repository root:

```sh
# Using default Aseprite installation path (/Applications/Aseprite.app/Contents/MacOS/aseprite)
npm run docs:screenshots

# Using a custom Aseprite installation path
ASEPRITE_PATH=/path/to/aseprite npm run docs:screenshots
```

### Fast Local Filtering (`--suite`, `--only`, `--theme`)

During development, you can capture and update a specific suite, individual screenshot IDs, or a single theme:

```sh
# Run only the fonts suite across both themes
npm run docs:screenshots -- --suite=fonts

# Capture only specific screenshot IDs in the dark theme
npm run docs:screenshots -- --only=font-upload,import-json --theme=dark

# Capture all 16 modal alerts across both themes
npm run docs:screenshots -- --suite=alerts
```

You can also validate and publish an existing capture directory manually:

```sh
node scripts/screenshots/publish.mjs <capture-directory>
```

## Adding New Screenshots

To add a new dialog, loading state, or alert to the automated capture suite:

1. Add an entry to `screenshots` in [`catalog.json`](catalog.json) with its `id`, `category`, `suite`, `kind`, and optional `variant` (for state variants or untitled alerts). No dialog header title is needed.
2. Add the corresponding `DialogHandle` or `captureAlert` call to the matching suite in `scripts/screenshots/suites/`.
3. Test the new capture quickly with `npm run docs:screenshots -- --only=<new-id>`, then run `npm run docs:screenshots` to regenerate the full suite and `docs/SCREENSHOTS.md`.
